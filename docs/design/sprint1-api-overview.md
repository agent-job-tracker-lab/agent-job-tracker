# Sprint 1 API一覧・入出力概要

## 1. このドキュメントの目的

本書は、Sprint 1の要求、ユーザーフロー、画面およびワイヤーフレームを、バックエンドが提供するAPIの責務へ対応付けるための概要設計書である。

以下を目的とする。

- Sprint 1で必要なAPIと責務を一覧化する
- 画面、ユースケース、APIの対応関係を明確にする
- 各APIの主要な入力、出力、正常結果およびエラーを整理する
- 要求で確定した業務ルールをAPIへ反映する
- Developerが採用した技術設計、その理由および代替案を記録する
- 製品判断が必要な未決事項と、後続の詳細設計事項を分離する

本書はAPIの概要設計を対象とし、OpenAPI定義、厳密なJSON Schema、DBスキーマおよびフレームワーク固有の実装構成は対象外とする。

---

## 2. 対象範囲

### 2.1 対象

- ログイン、ログアウト
- AgentCompanyの一覧取得、詳細取得、登録、更新、削除
- Jobの一覧取得、詳細取得、登録、更新、削除
- Applicationの現在ステータス取得、ステータス更新
- 未認証アクセス、入力エラー、対象なし、業務ルール違反、サーバー処理失敗
- デスクトップとスマートフォンから共通利用するAPI

### 2.2 対象外

- 利用者向けユーザー登録
- パスワード再設定
- Application単独の登録、編集、削除
- ステータス変更履歴の表示API
- Sprint 2以降のスキルシート、面談、次回アクション、重複警告、ダッシュボード、通知、CSV取り込み
- 詳細な入力型、最大長、NULL可否
- DBのテーブル・カラム構成
- 認証プロバイダーおよび認証ライブラリの選定
- OpenAPIファイルの作成

## 3. 記載区分

本書では、記載内容を次の3種類に分ける。

|区分|意味|
|---|---|
|確定事項|要求定義書、決定資料、DESIGN-01〜03から確定できる製品仕様|
|Developer案|製品の振る舞いを変えない範囲で採用したAPI技術設計。PRレビュー対象|
|未決事項|製品判断または後続の詳細設計が必要で、本書では確定しない事項|

APIパス、HTTPメソッド、JSONの命名などはDeveloper案であり、製品要求そのものではない。

## 4. API設計の基本方針（Developer案）

### 4.1 RESTを中心としたリソース設計

- AgentCompany、Job、Applicationをリソースとして扱う
- 取得は`GET`、登録は`POST`、部分更新は`PATCH`、論理削除は`DELETE`を使用する
- APIの基底パスを`/api`とする
- Sprint 1ではURLへバージョン番号を含めない
- パスは名詞、複数形、kebab-caseで統一する
- デスクトップとスマートフォンで同じAPIを使用する

本プロジェクトは単一クライアントを前提とする小規模MVPであり、初期段階から`/api/v1`を固定する利点が小さいため、バージョン番号を含めない。ただし、公開API化や複数クライアント対応が発生した場合は再検討する。

### 4.2 命名規則

- APIパスは英語の名詞、複数形、kebab-caseを使用する
- パスパラメータは`{resourceNameId}`の形式とし、lowerCamelCaseを使用する
- クエリパラメータとJSONのプロパティはlowerCamelCaseを使用する
- 真偽値は`is`、`has`、`can`など、意味が判断できる接頭辞を使用する
- 日付は`Date`、日時は`At`の接尾辞を使用する
- API IDは認証を`AUTH`、AgentCompanyを`AC`、Jobを`JOB`、Applicationを`APP`とし、カテゴリ内の連番を付ける
- 業務上の列挙値はAPI内部で一貫した英語の定数名を使用し、最終名称は詳細設計で決定する

上記はAPI契約を読みやすくするためのDeveloper案であり、DBのテーブル名やフレームワーク内部のクラス名までは規定しない。

### 4.3 JobとApplicationの扱い

- Job登録は`POST /api/jobs`の1回で受け付ける
- サーバーはJobと初期ステータス「未応募」のApplicationを同一トランザクションで作成する
- 一方だけが保存された状態は正常完了としない
- Job一覧・詳細のレスポンスにApplicationの現在ステータス概要を含める
- Application単独のCRUD APIは提供しない
- Applicationの現在ステータス取得・更新は、1対1関係を表すJob配下のサブリソースとして扱う

### 4.4 論理削除

- `DELETE`はクライアントにとっての削除操作を表す
- サーバー内部ではAgentCompanyまたはJobへ削除日時を記録する論理削除として実行する
- 削除済みデータは通常の一覧、詳細、検索対象に含めない
- Job削除時もApplicationとステータス変更履歴を保持する
- 削除済みデータの取得、復元、完全削除APIはSprint 1では提供しない

### 4.5 トランザクション

以下は一つの処理単位として、すべて成功するか、すべて失敗するかのどちらかにする。

- Job登録とApplication自動作成
- Applicationのステータス更新、更新日時保存、ステータス変更履歴作成
- AgentCompanyまたはJobの論理削除と削除日時保存

具体的なトランザクション境界、分離レベルおよびORMの実装方法はデータ設計・実装工程で決定する。

### 4.6 認証と認可

- ログインAPI以外は認証を必須とする
- MVPは事前作成した1ユーザーのみを対象とする
- 複数ユーザー間の権限制御はSprint 1で実装しない
- 認証方式、認証情報の項目、Cookieまたはトークンの使用は認証設計で決定する
- 未認証の場合は`401 Unauthorized`を返す

### 4.7 正常レスポンス

単一リソースの成功レスポンスは、不要な共通`data`ラッパーを設けず、対象リソースを直接返す。

一覧レスポンスは次の構造を基本とする。

```json
{
  "items": [],
  "pageInfo": {
    "page": 1,
    "pageSize": 20,
    "totalCount": 0,
    "totalPages": 0
  }
}
```

上記の件数は構造例であり、デフォルト値と最大値は後続設計で決定する。

### 4.8 エラーレスポンス

エラーはHTTPステータスコードに加えて、クライアントが処理を判定できる機械可読な`code`を返す。

```json
{
  "code": "VALIDATION_ERROR",
  "message": "入力内容を確認してください。",
  "fieldErrors": [
    {
      "field": "fieldName",
      "code": "REQUIRED",
      "message": "入力してください。"
    }
  ]
}
```

- `message`と`fieldErrors[].message`の最終文言は入力・エラー設計で決定する
- 内部例外、SQL、スタックトレース、認証情報などをレスポンスへ含めない
- 同じ原因には同じエラーコードを使用する
- 予期しないサーバーエラーは`500 Internal Server Error`とする

### 4.9 ID、日付、日時

- IDはクライアントが構造を解釈しない不透明な文字列として返す
- UUID、連番などの生成方式はデータ設計で決定する
- 日付はISO 8601の`YYYY-MM-DD`形式とする
- 日時はタイムゾーンを含むISO 8601形式とし、APIではUTCを基本とする
- 画面上の日本時間への変換はクライアントの表示責務とする
- 項目名は日付に`Date`、日時に`At`の接尾辞を使用する

### 4.10 一覧、検索、絞り込み

- 一覧APIは`page`と`pageSize`によるページ番号方式を採用する
- Sprint 1の通常データ量である案件100件を扱えることを前提とする
- Job一覧では`q`と`applicationStatus`をSprint 1の候補とする
- 勤務形態、都道府県、技術、リモート可否の詳細な絞り込みは要求として存在するが、具体的なUIはSprint 2のため、Sprint 1で有効にする範囲は未決とする
- AgentCompany一覧の`q`はワイヤーフレームにある検索欄へ対応するDeveloper案とする
- 未指定時の並び順は未決とし、詳細設計で確定する
- 論理削除済みデータを含めるクエリは提供しない

## 6. 共通HTTPステータスコード

|ステータス|用途|
|---|---|
|200 OK|取得、更新、ログイン、ログアウトの成功|
|201 Created|AgentCompanyまたはJobの登録成功|
|204 No Content|論理削除の成功|
|400 Bad Request|JSON不正、パラメータ形式不正など、リクエストを解釈できない場合|
|401 Unauthorized|未認証、認証情報不正、認証状態失効|
|404 Not Found|対象が存在しない、または通常APIから参照できない削除済み対象|
|409 Conflict|現在状態と競合する操作、関連JobによりAgentCompanyを削除できない場合、同一ステータス更新|
|422 Unprocessable Content|必須項目、値域、列挙値、項目間整合性などの入力検証エラー|
|500 Internal Server Error|予期しないサーバーエラー|

認証方式によって必要となる`403 Forbidden`、`419`相当の扱い、CSRFエラーなどは認証設計で決定する。

## 7. API詳細

## 7.1 AUTH-01 ログイン

|項目|内容|
|---|---|
|目的|事前作成された1ユーザーの認証情報を検証し、保護対象APIを利用できる認証状態を開始する|
|対応画面|SCR-01|
|対応ユースケース|UC-01|
|認証|不要|
|HTTPメソッド・パス|`POST /api/auth/login`|
|パスパラメータ|なし|
|クエリパラメータ|なし|
|主なリクエスト|認証情報。具体的な項目名は認証方式決定後に定義する|
|主なレスポンス|認証済みユーザーの識別情報、認証状態の有効期間など認証後画面に必要な最小情報|
|正常時の結果|認証状態を開始し、クライアントはSCR-02へ移動できる|
|主なステータス|`200`、`400`、`401`、`422`、`500`|
|想定エラー|未入力、認証情報不正、認証処理失敗|
|業務ルール|利用者向けユーザー登録は行わず、事前作成した1ユーザーのみを対象とする|
|後続設計|認証方式、認証項目、Cookie/トークン、セッション有効期間、CSRF対策|

認証情報の具体的な項目が未決であるため、`email`や`password`を確定項目として記載しない。

## 7.2 AUTH-02 ログアウト

|項目|内容|
|---|---|
|目的|現在の認証状態を解除し、保護対象APIを利用できない状態にする|
|対応画面|SCR-02〜SCR-09、UI-05|
|対応ユースケース|UC-11|
|認証|必要|

|パスパラメータ|なし|

|主なリクエスト|原則としてリクエストボディなし|
|主なレスポンス|ログアウト成功結果。Developer案では`200`と最小の結果を返す|
|正常時の結果|サーバー側の認証状態を無効化し、クライアントはSCR-01へ移動する|
|主なステータス|`200`、`401`、`500`|
|想定エラー|未認証、認証状態の解除失敗|
|業務ルール|ログアウト後は保護対象画面・APIへアクセスできない|
|後続設計|クライアント側のみで完了する方式か、サーバー側無効化が必要か|

ログアウトを`204`とする方法もあるが、認証方式が未決であり、処理結果を画面で判定しやすい`200`をDeveloper案とする。

## 10. 既存資料から確定できる内容

### 10.1 認証

- ログイン画面以外の画面とAPIは認証が必要である
- 事前作成した1ユーザーのみがログインする
- 利用者向けユーザー登録とパスワード再設定はMVP対象外である
- 未認証状態では保護対象を表示しない
- ログアウト後は認証状態を解除する

### 10.2 AgentCompany

- 会社名、担当者名、連絡先、特徴、最終連絡日、状態を登録・編集する
- 状態は「積極対応中」「保留」「終了」である
- 担当者情報はAgentCompany内に1名分だけ保持する
- 関連Jobが存在するAgentCompanyは削除できない
- 関連JobがないAgentCompanyは論理削除できる
- 削除済みAgentCompanyは通常一覧へ表示しない

### 10.3 Job

- 必須項目は案件名、紹介元AgentCompany、勤務形態である
- 勤務形態は「フルリモート」「ハイブリッド」「常駐」「未確認」である
- 単価は下限・上限の両方、片方のみ、両方未入力を許可する
- 下限と上限の両方がある場合は、下限が上限以下である必要がある
- 勤務地は都道府県と任意の補足項目を保持する
- Jobは論理削除し、通常一覧・検索へ表示しない
- Job削除後もApplicationなどの履歴データを保持する

### 10.4 Application

- JobとApplicationはSprint 1で1対1である
- Job登録時に「未応募」のApplicationを1件自動作成する
- JobとApplicationの一方だけが保存された状態を正常完了としない
- Application単独の登録・編集・削除画面および削除APIは提供しない
- 現在のステータスに関係なく、定義済みの全ステータスへ変更できる
- Sprint 1では通常の次ステータスを優先表示しない
- 同一ステータスでは更新せず、更新日時と履歴も変更しない
- ステータス変更時は変更前後、変更日時、変更者を履歴として保存する
- ステータス変更と履歴保存の一方だけを正常完了としない

### 10.5 クライアント

- デスクトップとスマートフォンは原則として同じAPIを使用する
- スマートフォンでは閲覧、ログイン、ログアウト、応募ステータス更新を利用できる
- スマートフォンではAgentCompanyとJobの登録、編集、削除を利用できない

## 11. 採用した主要な技術判断と理由

|判断|採用案|理由|
|---|---|---|
|API形式|REST中心|CRUDとリソースの対応が明確で、Sprint 1の規模に適する|
|バージョン|URLへ含めない|単一クライアントのMVPであり、早期の固定を避ける|
|更新|`PATCH`|編集画面で変更した項目だけを送れる|
|論理削除|`DELETE`で公開|クライアントは削除意図を表し、内部保存方式を隠蔽できる|
|Job登録|Job APIへApplication作成を内包|業務操作が一つであり、一貫性を保証しやすい|
|Applicationパス|Job配下の単数サブリソース|Sprint 1の1対1関係と画面のJob起点操作を表現できる|
|Job取得|Application概要を含める|一覧・詳細の初期表示で追加通信を避ける|
|一覧レスポンス|`items`と`pageInfo`|空状態、件数、将来のページ操作を同じ構造で扱える|
|ページング|ページ番号方式|100件程度のMVPで理解・実装・テストが容易|
|成功レスポンス|リソースを直接返す|不要なラッパーを避け、単純なクライアントにする|
|エラー|HTTPステータス＋共通エラーコード|画面表示とプログラム分岐の両方に利用できる|
|ID|不透明な文字列|DBの主キー方式をAPI利用者へ漏らさない|
|日時|ISO 8601、UTC|タイムゾーン解釈を明確にし、標準ライブラリで扱いやすい|
|同一ステータス更新|`409 Conflict`|現在状態と要求が競合し、保存を行わないことを明示できる|

## 12. 代表的な代替案との比較

|論点|採用案|代表的な代替案|違い|
|---|---|---|---|
|API形式|REST|GraphQL|GraphQLは柔軟な取得が可能だが、Sprint 1には導入・スキーマ管理コストが大きい|
|バージョン|`/api/...`|`/api/v1/...`|`v1`は将来の破壊的変更を区別しやすいが、現時点では公開契約がない|
|更新|`PATCH`|`PUT`|`PUT`は全体置換が明確だが、未決項目を含むフォームでは意図しない上書きが起こりやすい|
|Job/Application登録|`POST /api/jobs`で同時作成|Job作成後にApplication作成APIを呼ぶ|分離方式は責務が明示的だが、部分成功と再試行制御が複雑になる|
|Application識別|Job配下のパス|`/api/applications/{applicationId}`|独立パスは将来の1対多に適するが、Sprint 1のJob起点操作にはID解決が増える|
|現在ステータス取得|JOB-01/02へ概要を含め、APP-01は実装判断を残す|APP-01を常に個別呼び出し|個別呼び出しは責務が明確だが、画面表示の通信回数が増える|
|一覧ページング|ページ番号|カーソル|カーソルは大量・頻繁更新データに強いが、100件規模では複雑さが上回る|
|成功レスポンス|直接リソース|`{data: ...}`共通ラッパー|ラッパーはメタ情報を統一できるが、単一APIでは冗長になる|
|論理削除|`DELETE`|`PATCH {deleted: true}`|PATCHは内部動作を表すが、DELETEの方が利用者の操作意図とHTTPの意味が一致する|
|同一ステータス|`409`|`200`でno-op、`422`|`200`は冪等だが誤操作を検出しにくい。`422`は入力値自体が不正ではない|
